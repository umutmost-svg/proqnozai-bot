# Административная панель SporBot / ProqnozAI — архитектура и план

Статус: **архитектура утверждена владельцем 2026-11-10** (вариант A2 — отдельный admin-процесс
на общей кодовой базе с Mini App) и служит основой реализации D1–D9. Код не менялся.
Архитектурное ревью Codex: 7 раундов, APPROVE.

**Разработка не начата.** D1 стартует только после утверждения дизайна панели в Figma и
отдельного разрешения владельца; если утверждённый макет потребует изменений в разделах,
метриках или admin-API, этот документ обновляется до начала кода.

Решения владельца от 2026-11-10:
- проверка реальных коэффициентов отложена до развёртывания Mini App на production; разовый
  скрипт для Dokploy не запускается, временная интеграция через Quick Tunnel не нужна;
- кредиты не активируются: готовится только фундамент, прогнозы бесплатны и без ограничений;
- панель — **отдельное веб-приложение для компьютера** (свой URL, своя авторизация, без
  Telegram/initData), несколько администраторов с персональными учётными записями;
- дашборд основного бота (`dashboard.py`) не меняется.

## 1. Аудит: что есть и чего не хватает

| Область | Есть (переиспользуем) | Не хватает |
|---|---|---|
| Пользователи | `users` в БД Mini App: Telegram id, имя, username, язык, `created_at`, `last_login_at` (`miniapp/store.py`) | активности по дням: `last_login_at` меняется только при новой сессии → DAU/WAU/MAU занижены |
| Сессии | `sessions` (хеш токена, срок, отзыв); CLI `revoke-user`, `revoke-all` | — (переиспользуем те же методы `Store`) |
| AI-разборы | квоты `ai_usage` (только текущие сутки, старые дни удаляются), кеш разборов, коды ошибок | журнала вызовов: токены (`response.usage` не читается), стоимость, задержка, исход |
| Быстрый прогноз / купоны | только лимит частоты в памяти | учёта вообще (даже в логах) |
| История прогнозов | отдельный файл `<db>.forecasts.db`, неизменяемые записи, автосверка, `status_counts()`, `evaluate()` (LogLoss, Brier, ECE по рынкам, hit rate, по турнирам и версиям, порог 300) | рядов по времени (объём по дням, качество по неделям) — считаются SQL по той же таблице |
| Спортивные API | `usage()` клиента, `lastError`/`lastSuccessAt`, обработка 429 — **в памяти** | истории запросов/ошибок/429/задержек; сбрасывается при перезапуске |
| Коэффициенты | хранилище в памяти, `fetched_at` линий | времени последней выгрузки (отложено вместе с коэффициентами) |
| Система | `/api/health` (ok/unavailable), логи `key=value` с `request_id` | версии сборки, uptime, состояния фоновых задач (прогрев таблиц/поиска, сверка), счётчиков ошибок |
| Админ-доступ | CLI `python -m miniapp.admin` (без web) | учётных записей, ролей, web-сессий, журнала действий |
| Кредиты | ничего (ближайшая основа — `ai_usage`) | всё (только фундамент) |
| Дашборд бота | Flask + Basic Auth, читает только `bot.db` через `stats_server.py` | для Mini App не подходит: другой источник данных, один общий токен, нет аудита, Chart.js с CDN несовместим с CSP |

Вывод: панели нужны прежде всего **данные во времени**, которые сейчас не сохраняются. Расчёты
(сверка, метрики качества, квоты, пользователи, сессии) уже есть и дублироваться не будут.

## 2. Варианты архитектуры

| | A1. Admin-API внутри процесса Mini App | **A2. Отдельный admin-процесс из того же кода, общие данные** | B. Полностью отдельный сервис |
|---|---|---|---|
| Код и бизнес-логика | общий | **общий пакет `miniapp`** (те же `Store`, `ForecastHistory`, метрики) | дублируется или вызывается по HTTP |
| Данные | те же файлы SQLite | **те же файлы SQLite** (общий том, WAL, как уже делает CLI) | своя БД + синхронизация |
| Поверхность атаки | admin-маршруты в публичном процессе Mini App | **admin-процесс не доступен с домена Mini App**; свой домен, свои секреты | отдельная, но + канал синхронизации |
| Отказоустойчивость | падение/нагрузка админки = Mini App | **изолированы** | изолированы |
| Эксплуатация | 1 приложение | 2 приложения Dokploy из одного образа | 2 кодовые базы, 2 деплоя |
| Состояние в памяти Mini App (квоты API, фоновые задачи) | видно напрямую | **нужно сохранять в БД** — это всё равно нужно для истории | нужно API |

**Выбор: A2.** Отдельный SPA для desktop + отдельное ASGI-приложение `miniapp.admin_web` из
того же пакета и того же Docker-образа (команда `miniapp-entrypoint admin-web`), отдельное
приложение Dokploy на том же сервере, общий том с файлами SQLite Mini App. Дублирования нет:
admin-API вызывает те же классы, что и Mini App. Изоляция: у админки свой домен, свой порт,
свои секреты, своя БД учётных записей; публичный процесс Mini App о ней ничего не знает.

Ограничение A2: SQLite в WAL работает между процессами одного хоста на локальном диске (общий
том Docker на одном сервере — подходит; сетевое хранилище — нет). Оба приложения обязаны жить
на одном сервере; это фиксируется в runbook.

## 3. Данные

Граница безопасности проходит по файлам (SQLite не умеет права на таблицы): всё, что пишет
публичный процесс Mini App, — неавторитетно; всё авторитетное (настройки, журнал действий,
кредиты, учётные записи) лежит там, куда Mini App не имеет доступа.

| Файл | Том | Пишет | Читает | Роль |
|---|---|---|---|---|
| `miniapp.db` (есть) | `/data` | Mini App; admin — только отзыв сессий (§4.6) | оба | пользователи и сессии; **схема не меняется**: старая версия Mini App отказывается открывать файл с незнакомыми таблицами (`_OWN_TABLES`), новая таблица сломала бы откат |
| `miniapp.forecasts.db` (есть) | `/data` | Mini App (прогнозы, сверка) | оба; admin — `mode=ro` | переиспользуется как есть |
| `miniapp.telemetry.db` (новый) | `/data` | только Mini App | оба; admin — `mode=ro` | счётчики и журналы событий; **неавторитетна**: можно потерять/восстановить целиком без последствий для денег и доступа |
| `admin.db` (новый) | **`/admin-data`, только в admin-контейнере** | только admin | только admin | учётные записи, сессии админов, настройки, журнал действий, (D8) кредиты |
| `runtime-policy.json` (новый) | `/data` | admin (публикует) | Mini App | опубликованная копия политики (§3.3); не авторитетна — источник истины в `admin.db` |

Права: `/data` — общая группа `proqnozai` (фиксированный gid в образе), файлы 0660, каталог
2770; entrypoint Mini App вместо `chown -R miniapp` выставляет группу и права (`chgrp -R`,
`chmod g+rw`), admin-пользователь входит в группу и не владеет файлами Mini App. `/admin-data` —
0700, владелец admin-пользователь, в контейнер Mini App не монтируется. D2 включает тесты:
видимость файлов из обоих контейнеров, перезапуск обоих (права не «съезжают»), Mini App не
видит `/admin-data`. SQLite WAL между контейнерами — один хост, локальный том; `immutable=1` не
используется; чтение в режиме `ro` может создать `-wal/-shm` — каталог это допускает.

### 3.1 Таблицы

`miniapp.telemetry.db` (пишет Mini App; версия схемы в `schema_version`, миграции только вперёд):

| Таблица | Назначение |
|---|---|
| `user_activity(day, user_id, first_at, last_at, requests, ai_opened, ai_created, quick_single_ok, quick_coupon_ok, quick_failed)` PK(day,user_id) | DAU/WAU/MAU, использование функций (§4a) |
| `ai_calls(id, at, user_id, event_id, model_requested, model_served, provider_outcome, app_outcome, error_code, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, latency_ms, price_version, cost_micro_usd)` | каждый платный вызов Anthropic (§3.4): `provider_outcome` — что ответил провайдер, `app_outcome` — дошёл ли разбор до пользователя |
| `api_usage(hour, provider, attempts, ok, errors, rate_limited, local_refusals, latency_ms_sum, latency_ms_max)` PK(hour,provider) | каждая попытка HTTP (включая повторы) отдельно от локальных отказов лимитера |
| `task_status(name, last_started_at, last_finished_at, last_ok_at, last_error_code, detail_json)` | фоновые задачи |
| `error_events(minute, source, code, count, last_request_id)` | ошибки по кодам, без содержимого; 30 дней |
| `provider_status(provider, at, used_today, daily_limit, used_last_minute, per_minute_limit, cooling_down_s, last_ok_at, last_error_code)` | текущий снимок квоты из памяти клиента (раз в 30 с); в админке старше 2 мин помечается «устарело» |

Цены моделей для оценки стоимости — неизменяемая таблица версий в коде (`miniapp/ai/prices.py`,
новая версия = новый релиз); номер версии пишется в каждый вызов.

`admin.db` (пишет только admin; одна транзакция = изменение + событие журнала):

| Таблица | Назначение |
|---|---|
| `admin_users`, `admin_sessions`, `admin_recovery_codes` | учётные записи, сессии, коды восстановления 2FA (хеши) |
| `runtime_settings(key, value_json, version, updated_at, admin_id)` | источник истины настроек (§3.3) |
| `pending_revocations(request_id, session_hashes, created_at)` | цели незавершённого отзыва сессий (§4.6); строка удаляется вместе с событием `completed`; незавершённые строки доводятся сразу при ошибке (повтор с паузой), при старте и раз в минуту; старше 1 ч — сигнал в System |
| `admin_events(id, at, admin_id, action, target_type, target_id, before_json, after_json, reason, idempotency_key, request_id, kind)` | `before_json`/`after_json` — только поля из белого списка для каждого типа действия (настройка: ключ и значение; роль: старая/новая; кредиты: баланс и дельта); хеши паролей, секреты 2FA, коды восстановления, токены и лишние персональные данные туда не попадают никогда (тест на каждый тип); **неизменяемые** события (триггеры запрещают UPDATE/DELETE); `kind` = `done` для атомарных действий или пара `requested` → `completed` для отзыва сессий (§4.6); статус выводится из событий |
| D8: `credit_accounts(user_id, balance, unlimited, updated_at)`, `credit_ledger(id, user_id, delta, balance_after, kind, reason, admin_id, idempotency_key UNIQUE, created_at)` | фундамент кредитов: баланс, запись ledger и событие журнала — в одной транзакции; ledger только добавление |

Запись телеметрии: счётчики (`user_activity`, `api_usage`, `error_events`) копятся в памяти и
сбрасываются одной транзакцией раз в 60 с и при штатной остановке (lifespan shutdown); при
аварийном падении теряется не больше минуты счётчиков. **`ai_calls` не копится**: каждый
платный вызов записывается сразу отдельной короткой транзакцией, поэтому расходы не теряются.
Внешние ключи между файлами не используются; ссылки на пользователя — по Telegram id.

### 3.2 Резервные копии, восстановление, откат
- `miniapp.db`: `restore_from` без изменений.
- `miniapp.telemetry.db`: копия/восстановление целиком (данные неавторитетны); версия схемы
  старее текущей — миграция вперёд, новее — отказ.
- `admin.db`: онлайн-копия каждый час (`admin backup`); **восстановление только в отсутствующий
  файл** (авария); поверх живого файла — отказ, чтобы старая копия не стёрла журнал, ключи
  идемпотентности и операции кредитов.
- Восстановление **закрыто по умолчанию и не опирается на полноту следа**: CLI `admin restore`
  переводит панель в режим восстановления, в котором:
  1) все восстановленные сессии, приглашения и коды восстановления 2FA отозваны;
  2) **у всех учётных записей сброшены пароль и 2FA** (входа по старым данным нет вообще);
  3) публикация политики приостановлена (§3.3);
  4) войти может только владелец по одноразовому токену из CLI; он заново задаёт себе пароль и
  2FA, проверяет список админов и роли (лишних отключает), сохраняет настройки (новая версия по
  времени — новее любой прежней) и завершает режим командой `admin recovery-complete` (§3.3); остальные админы входят только по новым приглашениям.
  Структурные строки журнала в логах контейнера — справочная информация для владельца
  (что менялось после копии), а не условие безопасности.
  Тесты: восстановление поверх живого файла — отказ; вход по данным из копии невозможен;
  старая политика из копии не публикуется; после `recovery-complete` версия политики выше
  прежней.
- Откат кода Mini App: старая версия не знает новые файлы — работает как раньше;
  admin-приложение останавливается. Тест: миграции на копии, откат на предыдущий релиз,
  повторный накат.

### 3.3 Настройки, применяемые на лету
Сейчас `Settings` неизменяем, а лимиты копируются в сервисы при старте — простое чтение
таблицы ничего бы не изменило. Механизм:
- **Источник истины** — `runtime_settings` в `admin.db`. **Версия политики** = `max(now_ms,
  последняя зафиксированная + 1, версия опубликованного снимка + 1, отметка применения Mini App
  + 1)` — admin читает оба файла на `/data` перед фиксацией; поэтому новая версия выше всего,
  что когда-либо публиковалось или применялось, даже после восстановления старой `admin.db` и
  при отставших часах.
- **Публикация:** полный снимок в `/data/runtime-policy.json` (временный файл + атомарное
  переименование). Admin публикует после каждого изменения, при старте и раз в 60 с, если
  файла нет или его версия ниже зафиксированной; в режиме восстановления публикация
  приостановлена. Файл снимка и отметка применения (ниже) **не входят ни в одну резервную
  копию и никогда не восстанавливаются**.
- **Отметка применения:** Mini App после успешного применения записывает версию в отдельный
  файл `/data/runtime-policy.applied` (атомарно) и отклоняет снимки с версией ниже этой
  отметки. Отметка не зависит от телеметрии; если она потеряна, принимается текущий снимок
  (он единственный, старые снимки не хранятся и не восстанавливаются).
- **Режимы Mini App:** `MINIAPP_RUNTIME_POLICY=off` (по умолчанию, до включения панели
  настроек) — значения env, как сейчас. `required` — при отсутствии или неверном снимке
  Mini App работает в **закрытом режиме**: каждая функция, у которой есть выключатель
  (`ai.enabled` → новые платные разборы, `quick.enabled` → быстрый прогноз и купоны),
  **выключена**, лимиты — минимальные из env; просмотр матчей и готовых разборов работает;
  сигнал в System. После появления верного снимка — обычный режим.
- В рабочем режиме Mini App перечитывает снимок раз в 30 с, проверяет схему и потолки env;
  неверный файл — остаётся последняя верная политика + `error_events`. Сервисы читают
  политику в начале запроса; начавшийся запрос доживает со своей.
- Переменные окружения — значения по умолчанию и **жёсткие потолки**.
- v1 ключи: `ai.enabled`, `ai.per_user_daily`, `ai.daily_budget`, `quick.enabled`;
  `credits.enabled` и `credits.forecast_price` — только отображение до разрешения. Модель AI,
  ключи, токены и секреты не редактируются. Маршрут быстрого прогноза получает проверку
  выключателя (сейчас её нет).
- Завершение восстановления (`recovery-complete`) требует, чтобы отметка применения Mini App
  была **ровно равна** новой опубликованной версии (не «не ниже»).
- Тесты: падение между фиксацией и публикацией; потеря снимка при старте с
  `quick.enabled=false` и `ai.enabled=false` (обе функции остаются выключенными); потеря
  отметки; неверный файл; восстановление старой `admin.db` → старая политика не публикуется;
  восстановление при отставших часах и отсутствующем снимке → новая версия всё равно выше
  отметки и принимается;
  каждый ключ «применено за ≤ 30 с, неверное значение отклонено».

### 3.4 Учёт AI-вызовов
Сейчас при отказе модели или обрезанном ответе клиент бросает исключение до того, как прочитаны
`usage`. В D1 граница с провайдером переделывается: каждый полученный ответ (успех, отказ,
обрезка, ответ, не прошедший проверку) сначала записывается в `ai_calls` с usage, моделью и
задержкой, и лишь потом проверяется; при сетевой ошибке/таймауте токены и стоимость — «нет
данных» (NULL), а не ноль. Экран расходов показывает число вызовов с неизвестной стоимостью
отдельно и не выдаёт сумму за полную.

### 3.5 Что не создаётся
Ни второго механизма сверки, ни копии пользователей или прогнозов, ни отдельной аналитической
БД. Forecast Analytics читает `forecasts.db` через `ForecastHistory(read_only=True)`; качество и
порог 300 — только существующий `evaluate()` (последняя строка до начала матча **на событие и
версию модели**); ряды по периодам — новые методы того же класса с теми же формулами
(`metrics.py`) и тем же отбором строк. Пустая история (новая установка) — явные пустые метрики
из общего метода, а не деление на ноль (исправляется в D5 с тестом). `evaluate()` читает всю
историю в память, поэтому в админке: одно общее вычисление на все одновременные запросы
(single-flight) с кешем на 5 минут, рабочий поток, ограничение работы SQLite через
`progress handler` (прерывание долгого чтения, чтобы не держать WAL); нагрузочный тест —
50 000 прогнозов, большой WAL, несколько одновременных «холодных» запросов; Mini App не должен
замедлиться.

## 4. Безопасность

### 4.1 Учётные записи и вход
- e-mail + пароль (`hashlib.scrypt`, стандартная библиотека) + **обязательная TOTP** (RFC 6238).
- Подключение 2FA: одноразовая ссылка (24 ч) → пароль → QR → подтверждение кодом → 10
  одноразовых кодов восстановления (хранятся хешами). Потеря телефона: код восстановления или
  сброс владельцем (действие в журнале).
- Секреты TOTP шифруются ключом `MINIAPP_ADMIN_ENC_KEY` (есть только у admin-контейнера);
  ротация ключа — CLI-командой перешифрования; ключ хранится в секретах Dokploy и в офлайн-копии
  владельца.
- Первый владелец — только CLI в контейнере (`admin create-owner`), не через web.
- Отдельный класс настроек admin-процесса: ему не нужны токен бота, ключи Anthropic и
  football-data; он их не получает.

### 4.2 Роли
`owner` — всё, включая админов, опасные настройки и кредиты; `admin` — пользователи, сессии,
настройки в пределах потолков; `analyst` — только чтение. Проверка на сервере для каждого
маршрута; интерфейс лишь скрывает недоступное.

### 4.3 Сессии и CSRF
Случайный токен, в БД хеш; cookie `__Host-` HttpOnly Secure SameSite=Strict; простой 30 мин,
абсолютный срок 12 ч; выход везде; список своих сессий. Для изменяющих запросов — CSRF-токен
сессии в заголовке + точная проверка Origin.

### 4.4 Защита от перебора и IP
Сервер, как и сейчас, не доверяет `X-Forwarded-*`. IP берётся только из `CF-Connecting-IP`
(Cloudflare перезаписывает его сам) и **только после успешной проверки edge-секрета**; прямые
запросы к серверу без секрета отклоняются раньше. Плюс правило rate limiting Cloudflare на
`/api/admin/auth/*`. Блокировка учётной записи после N ошибок хранится в `admin.db` и
переживает перезапуск; одинаковый ответ для неверного e-mail и пароля. Тесты: обход edge,
подмена заголовка без секрета.

### 4.5 Периметр
Отдельный домен `admin.<домен>` через Cloudflare (proxied) + рекомендуется Cloudflare Access
(бесплатно до 50 человек) как второй замок; свой edge-секрет; admin-API не маршрутизируется с
домена Mini App. Свой healthcheck admin-контейнера (`/api/admin/health`, без данных): общий
образ проверяет здоровье по режиму запуска (`serve` → `/api/health`, `admin-web` →
`/api/admin/health`); D2/D9 проверяют, что оба контейнера становятся healthy.

### 4.6 Изменяющие действия и аудит
- Действие и его событие журнала — **в одной транзакции `admin.db`**: настройки, учётные
  записи, роли, вход, 2FA и (D8) кредиты живут там же, где журнал.
- Отзыв сессий пользователя — единственная запись админки в чужой файл (`miniapp.db`):
  1) в одной транзакции `admin.db`: событие `requested` (владеет уникальным ключом
  идемпотентности и `request_id`) и строка в отдельной таблице `pending_revocations(request_id,
  session_hashes, created_at)` со **списком хешей конкретных сессий** (выбранных в момент
  запроса; хеши не попадают в бессрочный журнал); 2) отзыв ровно этих сессий в `miniapp.db`
  новым методом `Store`, который в одной транзакции отзывает выбранные сессии **и все сессии с
  тем же `init_hash`** (созданные из того же запуска, в том числе во время операции) и
  «сжигает» эти initData по правилам существующего `revoke_user_sessions` (повтор после
  падения идемпотентен; новые запуски с другим initData не затрагиваются); 3) событие `completed` (ссылается на `request_id`) и удаление строки
  `pending_revocations` — в одной транзакции. При старте
  `requested` без `completed` повторяются по тому же списку — новые сессии пользователя,
  созданные позже, не затрагиваются. Тест: падение между шагами, вход пользователя между
  шагами, вход с тем же initData между шагами 1 и 2 (такая сессия тоже отозвана), повторный
  вход с тем же initData после отзыва — отказ.
- Опасные действия (кредиты, роли, отзыв всех сессий, флаги): повторное подтверждение TOTP,
  привязанное к конкретному действию и цели (действует 5 мин), обязательная причина, ключ
  идемпотентности (уникален в журнале: повтор возвращает прежний результат).
- Кредиты: `credits.enabled=false`; в Mini App нет ни одного места списания до отдельного
  этапа; админ-операции с балансом в D8 выключены отдельным флагом и не влияют на доступ.

### 4.7 Frontend и ответы API
Только статические файлы без секретов; строгий CSP (self, без inline, без CDN — Chart.js в
бандле), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `noindex`. Ответы —
агрегаты и поля, нужные экрану; токены, ключи и хеши не возвращаются никогда; ошибки — коды
с `request_id`. Запросы аналитики ограничены по времени и размеру страницы, чтобы долгие
чтения не задерживали запись Mini App.

### 4.8 Персональные данные
Telegram id, username, имя, id событий в `ai_calls`, хеши IP и значения «до/после» в журнале
— персональные данные: видны только ролям admin/owner (analyst видит агрегаты без
идентификаторов); `user_activity` и `ai_calls` хранятся 400 дней, `error_events` 30 дней,
журналы — бессрочно; хеш IP — с секретной солью, без исходного адреса.

## 4a. Определения метрик

- **Активный пользователь за день** — уникальный Telegram id с хотя бы одним авторизованным
  запросом к API за сутки UTC (хранение в UTC, отображение в выбранном поясе по дням UTC с
  пометкой). WAU/MAU — уникальные за 7/30 суток (не сумма DAU).
- **Новые** — `users.created_at` в периоде.
- **AI-разбор создан** — разбор, доставленный пользователю (`ai_calls.app_outcome=delivered`);
  оплаченный, но не доставленный (не прошёл проверку, не записался) — отдельная строка расходов; **открыт** — показ
  разбора пользователю (включая кеш). Это разные числа и показываются раздельно.
- **Быстрый прогноз / купон** — успешный ответ с результатом; ошибки и «нет матчей» —
  отдельно.
- **Прогнозы модели** — строки `ai_forecasts` (одна на набор входных данных, не на просмотр);
  подписи явно различают: `status_counts()` считает строки, `evaluate()` — последнюю строку
  события до начала матча; качество и порог 300 — только по `evaluate()`.
- **Запросы к API** — каждая сетевая попытка, включая повторы; локальные отказы лимитера —
  отдельно; 429 — ответы провайдера с этим кодом.
- **Стоимость AI** — оценка: токены × цены из версии таблицы цен в коде (`miniapp/ai/prices.py`), записанной в вызове; не счёт
  провайдера.

## 5. Структура панели (desktop-first)

Каркас: боковое меню, верхняя панель (глобальный период: сегодня / 7 / 30 / 90 дней / свой
диапазон, часовой пояс Баку/UTC, обновлено N с назад), светлая и тёмная темы, адаптивность до
планшета. Все таблицы: сортировка, поиск, фильтры, пагинация на сервере, выгрузка CSV.

1. **Overview** — карточки: всего пользователей, новые за период, DAU / WAU / MAU, AI-разборы
   (созданные / просмотренные), быстрые прогнозы и купоны, прогнозы модели, расходы AI за
   период, состояние системы (светофор). Графики: активные и новые по дням/неделям/месяцам,
   использование функций, расходы по дням. Каждая карточка ведёт в свой раздел.
2. **Users** — таблица (Telegram ID, username, имя, язык, регистрация, последняя активность,
   AI-разборы, быстрые прогнозы, сессии), поиск по id/username/имени, фильтры (новые,
   активные, неактивные N дней, язык). Карточка пользователя: профиль, активность по дням
   (график), использование функций, AI-вызовы (время, исход, стоимость — без содержимого),
   сессии с отзывом, кредиты (∞ / баланс, пока «выключено»), журнал действий админов по
   этому пользователю.
3. **Forecast Analytics** — всего / ожидают / сверены / аннулированы, hit rate рекомендаций,
   доля NO_BET, LogLoss и Brier 1X2, ECE по рынкам, по турнирам, динамика по неделям,
   прогресс к 300 матчам проспективной проверки, сравнение версий моделей (когда их станет
   больше одной), список прогнозов с фильтрами и карточкой (вероятности, рекомендация, итог,
   журнал ревизий итога).
4. **AI Analytics & Costs** — вызовы, успешные/ошибки по кодам, токены (вход/выход/кеш),
   стоимость за период и прогноз на месяц, средняя и p95 задержка, по моделям, по дням,
   доля ответов из кеша, использование квот (на пользователя и общий бюджет), топ
   пользователей по расходу.
5. **API Monitoring** — football-data: запросы, ошибки, 429, задержки по часам, текущая квота
   (сутки/минута — снимок `provider_status` со временем, «устарело», если старше 2 мин), последнее успешное обновление и последняя ошибка, свежесть кеша турниров;
   коэффициенты — «отключено до production».
6. **Credits** — экран с пометкой «выключено»: стандартная цена прогноза
   (`credits.forecast_price`, только отображение),
   поиск пользователя, баланс/∞, история операций; кнопки начисления/списания/безлимита
   отображаются, но неактивны до отдельного разрешения.
7. **System & Logs** — версия (git SHA сборки), uptime, состояние БД (размер, WAL),
   фоновые задачи (последний запуск/успех/ошибка), интеграции (Anthropic, football-data,
   Telegram), ошибки по кодам и минутам с `request_id` (без содержимого запросов).
8. **Admin Settings** — администраторы и роли (owner), мои сессии и 2FA, настройки
   приложения из белого списка (§3.3: выключатель и лимиты AI, выключатель быстрого прогноза;
   модель AI и цены — только просмотр), журнал действий с фильтрами.

### Основные сценарии администратора
- Утро: Overview за вчера → аномалия (рост ошибок/расходов) → AI Costs / System по ссылке.
- Пользователь пишет в поддержку: поиск по username → карточка → активность и ошибки его
  AI-вызовов → при необходимости отзыв сессий (с причиной, в аудит).
- Неделя модели: Forecast Analytics → сверено/ожидает → динамика LogLoss/Brier → турниры.
- Контроль расходов: AI Costs за месяц → прогноз → при необходимости снизить лимит в
  Admin Settings (Mini App применит за ≤ 30 с, действие в аудите).
- Новый сотрудник: owner создаёт учётную запись с ролью analyst → тот задаёт пароль и 2FA
  по одноразовой ссылке.

## 6. Admin-API (кратко)

`/api/admin/auth/{login,totp,logout,sessions}`, `/api/admin/overview?from&to&tz`,
`/api/admin/users`, `/api/admin/users/{id}`, `/api/admin/users/{id}/sessions/revoke`,
`/api/admin/forecasts/{summary,series,list,{key}}`, `/api/admin/ai/{summary,series,calls}`,
`/api/admin/api-usage`, `/api/admin/system`, `/api/admin/settings`, `/api/admin/admins`,
`/api/admin/audit`, `/api/admin/credits/*` (только чтение до включения). Все — JSON, только
GET для чтения; изменения — POST/PATCH с CSRF, ролью и аудитом.

## 8. Риски

- Общий SQLite между двумя приложениями: только один хост и локальный том; запись
  админки — короткие транзакции `IMMEDIATE`, как у CLI.
- Запись `user_activity` на каждый запрос нагрузила бы SQLite: счётчики копятся в памяти и
  сбрасываются пакетом (потеря ≤ 1 минуты при падении допустима).
- Стоимость AI — расчётная по таблице цен (не счёт провайдера); показывается с пометкой
  «оценка», версия цен хранится.
- Исторических данных до D1 нет: активность и расходы начнут копиться с момента выкладки
  D1 (пользователи и прогнозы — с начала).
