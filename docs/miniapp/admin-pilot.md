# Админ-панель SporBot — локальный пилот

Пилот desktop-панели по архитектуре `admin-dashboard.md` (вариант A2) и утверждённым макетам Figma
`SporBot CRM v2` (страница «SporBot CRM v2» файла vITwWcayF5jgfubMw1Sprc). Только для оценки интерфейса и сценариев на этом компьютере:
слушает `127.0.0.1`, не подключается к production, стенду и боту, ничего не деплоит.

## Запуск

Один раз (зависимости):

```bash
cd admin-frontend && npm install && npm run build && cd ..
```

Создать данные пилота (папка вне репозитория, по умолчанию `~/.sporbot-admin-pilot`, права 0700):

```bash
miniapp/.venv/bin/python -m miniapp.admin_web init
```

Команда создаёт демо-набор (64 пользователя и 40 прогнозов через те же классы `Store` и
`ForecastHistory`, что и Mini App) и три учётные записи: `owner@sporbot.local`,
`admin@sporbot.local`, `analyst@sporbot.local`. Пароли и секреты 2FA записываются только в
`~/.sporbot-admin-pilot/credentials.txt` (0600), в терминал и репозиторий не попадают.

Запуск сервера:

```bash
miniapp/.venv/bin/python -m miniapp.admin_web serve
```

Открыть `http://127.0.0.1:8795`. Код 2FA: строку `otpauth://` из `credentials.txt` можно добавить
в приложение-аутентификатор или получить текущий код командой

```bash
miniapp/.venv/bin/python -m miniapp.admin_web code owner@sporbot.local
```

Код одноразовый: для каждого следующего подтверждения нужен новый (новый шаг 30 с).

**Остановить:** `Ctrl+C` в терминале сервера. **Открыть снова:** повторить `serve` (данные
сохраняются). **Начать с чистого листа:** удалить `~/.sporbot-admin-pilot` и выполнить `init` (нужно и после обновления пилота: схема `admin.db` пилота не мигрируется).
Переменные: `ADMIN_PILOT_DIR` (папка данных, только вне репозитория), `ADMIN_WEB_PORT` (порт, по умолчанию 8795),
`ADMIN_BOT_USERNAME` и `ADMIN_MINIAPP_SHORT_NAME` (необязательно: имена для готовых реферальных ссылок).

## Разделы

Аналитика (6 вкладок) · Пользователи (быстрые сегменты, теги, массовые действия) · карточка пользователя 360°
(хронология, сообщения, кредиты, сессии, заметки, блокировка) · Диалоги · Рассылки (список, редактор с превью
Telegram, планирование) · Сегменты (конструктор правил) · Кредиты (журнал, групповые операции, правила) ·
Прогнозы · AI и расходы · Спортивные API · Система · Настройки (функции, администраторы, журнал действий).

## Что настоящее, что демо

| Данные | Источник в пилоте |
|---|---|
| Пользователи, сессии, отзыв сессий | `miniapp.db` пилота через `Store` (демо-набор, id от 990000000) |
| Прогнозы, сверка, журнал ревизий, LogLoss/Brier, порог 300, популярные лиги | `miniapp.forecasts.db` через `ForecastHistory(read_only=True)` |
| Регистрации по дням и часам, языки | реальные данные `users` (демо-набора) |
| Теги, заметки, сегменты, рассылки, сообщения, кредиты, блокировки | `admin.db` — настоящая логика; при `init` добавлен демо-набор CRM (причина «демо») |
| Учётные записи, вход, 2FA, роли, журнал, настройки | `admin.db` — настоящая логика |
| Гео, платформы, активность по часам, когорты, источники, функции, DAU, AI-вызовы, API, диалоги | **не собираются до D1**: пустые состояния; «Демо-телеметрия» показывает вымышленные данные с пометкой «ДЕМО» |

## Ограничения пилота (снимаются на этапах D1–D9)

- Только режим `local-pilot`: cookie без `Secure`/`__Host-` (http на loopback), без edge-секрета
  и Cloudflare Access. Серверного режима в коде нет — его добавит D2.
- Секреты TOTP хранятся в `admin.db` (0600) без шифрования `MINIAPP_ADMIN_ENC_KEY` (D2).
- Изменения настроек пишутся в `admin.db` и журнал, но **не публикуются** в Mini App (D7).
- Рассылки и личные сообщения **сохраняются, но не отправляются** в Telegram: у admin-процесса нет токена
  бота; отправка — через внутренний канал бота (отдельный этап с ревью архитектуры).
- Диалоги — только демо: приём сообщений пользователей требует решения о хранении переписки
  (правило приватности проекта).
- Кредиты — учёт без списаний в Mini App; блокировка — флаг + выход со всех устройств, Mini App её пока не проверяет.
- Сегменты и списки пользователей считаются в памяти (до 50 000 пользователей) — для production нужен SQL.
- Приглашение администратора создаёт запись «приглашён», ссылка активации не выдаётся (D2).
- Отзыв сессий — события `requested` → `completed`; незавершённый запрос доводится повтором с тем же
  ключом, но без таблицы `pending_revocations` и фонового довода (D4), и отзываются все сессии,
  активные на момент завершения, а не список, зафиксированный при запросе; при сбое после записи в
  `miniapp.db`, но до события `completed`, повтор запишет `revoked: 0` (точный счёт — D4).
- `init` работает только с новой пустой папкой, `serve` открывает только папку с маркером
  демо-набора (`pilot.json`) и правами 0700: папку стенда или production пилот не откроет.
- Телеметрии нет (D1), версии сборки нет (D7), кешей и ограничений тяжёлых запросов
  `evaluate()` нет (D5).
- Пилот не входит в Docker-образ стенда.

## CRM: активность, GEO, история ID MB (ветка `feat/admin-crm`, этап 1)

- **Активность** в списке и карточке — из `miniapp.telemetry.db` (`user_activity`, только чтение, `mode=ro`):
  последняя активность (позднее из последнего входа и последней активности), прогнозы (быстрые + купоны +
  созданные AI-разборы), активные дни за 30, AI создано/открыто, график по дням. Телеметрию пишет Mini App только
  при `MINIAPP_ADS_ENABLED=true`; без неё — «—» и пояснение, ошибок нет.
- **GEO** — код страны от edge из `ad_events.country` (IP не хранится нигде); если его нет — догадка по языку
  интерфейса только для однозначных (az→AZ, tr→TR, uz→UZ; португальский не угадывается) с пометкой «по языку». Внешних гео-сервисов нет.
- **История ID MB** — `crm_mb_id_history` (старое → новое значение, кто, когда; видна ролям с `read_personal`);
  в неизменяемый журнал по-прежнему попадает только факт изменения.
- **Блокировка** — быстрый сегмент «Заблокированные», история блокировок/разблокировок с причинами в карточке.

## Реферальные ссылки (этап 2)

- Ссылки — `crm_referral_links` в `admin.db` (код `[a-z0-9]{3,24}`, название, канал `bot`/`miniapp`, архив). Создание и
  архив — право `manage_referrals` (owner, admin); в журнал — id, код и канал, без названия. Статистика — только
  агрегаты, видна аналитику.
- Ссылка бота `https://t.me/<бот>?start=ref_<код>`, Mini App — `https://t.me/<бот>/<app>?startapp=ref_<код>`; имена
  берутся из `ADMIN_BOT_USERNAME` и `ADMIN_MINIAPP_SHORT_NAME` (не заданы — показывается только параметр).
- Атрибуция — только первый запуск: бот пишет `(user, code)` в `bot-crm.db` (`BOT_CRM_DB` + `BOT_REFERRALS_ENABLED=true`,
  только если пользователя ещё нет в `bot.db`; ошибка файла не мешает `/start`); Mini App — в `miniapp.db`
  `user_attribution` в той же транзакции, что создаёт пользователя (`MINIAPP_REFERRALS_ENABLED=true`). При двух
  атрибуциях источник — более ранняя. Существующие `/start` и callback_data не меняются; другие payload игнорируются.
- Воронка на ссылку: запуски → есть аккаунт Mini App → из них запросили прогноз (по телеметрии); «активны 7 дней» —
  тоже среди дошедших до Mini App.
  Список пользователей фильтруется по коду (`/users?ref=<код>`), в списке и карточке — колонка «Источник».

## Обращения и история взаимодействия (этап 3)

- Сбор — только новые входящие личные текстовые сообщения боту и только при `BOT_INQUIRIES_ENABLED=true` + `BOT_CRM_DB`
  (без флага обработчик даже не регистрируется). Команды, кнопки меню, группы и сообщения `ADMIN_ID` не сохраняются.
  Старые сообщения не собираются и не восстанавливаются: сообщения, отправленные до запуска бота с включённым флагом
  (в т. ч. накопленные Telegram за время простоя), пропускаются по времени отправки. Обработчик в группе −1 никогда не останавливает обычную
  обработку; ошибки хранения пишут в лог только тип ошибки.
- Перед первым сохранением пользователь получает одноразовое уведомление `inquiry_notice` (7 языков, срок хранения
  подставляется и запоминается); если уведомление не доставлено — сообщение не сохраняется. Сообщения пользователя
  никогда не хранятся дольше срока, названного ему в уведомлении (даже если срок потом увеличат).
- Хранение: `bot-crm.db` → `inquiries` (текст ≤ 2000 символов). Срок — `config.retention_days` (1–365, по умолчанию 90),
  меняет только владелец (право `manage_inquiry_settings`, причина + 2FA + ключ идемпотентности, журнал
  `inquiry.retention` с прежним и новым значением). Источник истины — `crm_inquiry_retention` в admin.db (в одной
  транзакции с журналом); затем значение применяется к `bot-crm.db` с удалением старых сообщений; если файл не
  записался — ответ 503 `retention_not_applied`, повтор того же запроса или старт админки применяет его. Удаление —
  сразу при изменении, админкой при старте и перед каждым чтением обращений (не удалось — 503, тексты не
  показываются), ботом — не чаще раза в час при записи. Файл `bot-crm.db` — строго 0660 (проверяется перед каждой
  записью с обеих сторон; если сделать его приватным нельзя — запись отклоняется).
- Доступ: `read_personal` + явное право `view_dialogs` (выдаёт владелец) — для списка, переписки и настроек; список
  не содержит текстов, каждое открытие переписки — событие журнала `inquiry.view` (только id). Статус обращения (открыто/закрыто, `crm_inquiry_status` в admin.db) — `manage_users` +
  право; новое сообщение пользователя снова открывает обращение. Ответ — через очередь бота (`bot-outbox.db`),
  история объединяет входящие и наши сообщения со статусом доставки.

## Очередь, роли, продуктовая аналитика (этап 4)

- **Очередь отправки** (`/outbox`, `read_personal`): счётчики по статусам (всего и за 24 ч), ближайшее задание,
  последняя отправка, последние 100 заданий без текстов (тип, получатель, статус, попытки, код ошибки), лимиты бота
  (`bot_outbox.py`; тест держит значения равными) и журнал действий с очередью. Подключение очереди к боту
  (`main.py`, `BOT_OUTBOX_ENABLED`) по-прежнему отдельный шаг.
- **Роли и права** (Настройки → Роли и права): матрица `PERMISSIONS` с сервера; владелец выдаёт/отзывает отдельные
  права (`view_dialogs`) с причиной и 2FA. Новые права этапа: `manage_referrals` (owner, admin),
  `manage_inquiry_settings` (owner).
- **Продуктовая аналитика** (`/product`, агрегаты, видна аналитику): DAU по UTC-дням, WAU/MAU (уникальные), прогнозы
  (быстрые + купоны + AI), AI создано/открыто, недельные когорты регистрации с удержанием по неделям от собственной
  регистрации, реферальная воронка. Источник — `miniapp.telemetry.db` (ведётся при `MINIAPP_ADS_ENABLED=true`); без неё —
  «не собирается». Покрытие коэффициентами не собирается (коэффициенты в памяти Mini App) — отдельный шаг.
- **Реклама**: изолированный маршрут-заглушка `ads/*` (`AdsPlaceholder` в `pages/Ops.tsx`). После слияния
  `feat/ads-module` — одна строка в `App.tsx`: `import { AdsRoutes } from './ads'` и
  `<Route path="ads/*" element={<AdsRoutes />} />`; пункт меню — `ADS_NAV_LINK` из `./ads` вместо `['/ads', 'Реклама']`.
- **Отмена рассылки против постановки в очередь** (две БД): задания рассылки вставляются «на удержании»
  (`retry_at = HOLD`, бот их не берёт), статус в `admin.db` читается снова, и только запланированная рассылка их
  освобождает. Отмена отмечает пакет в `bot-outbox.db` (`cancelled_batches`, общая схема с `bot_outbox.py`) вместе с
  отменой его `queued`-заданий одной транзакцией; постановка, освобождение, выдача боту и повтор после RetryAfter
  проверяют эту отметку в том же файле, поэтому SQLite их упорядочивает.
- **Известный P2 (закрыть до подключения `BOT_OUTBOX_ENABLED`)**: отмена коммитится в `admin.db` раньше отметки в
  `bot-outbox.db`; если процесс админки упадёт между ними, наступившие задания остаются доступны боту до перезапуска
  админки (при старте отмена дописывается). Бот после выкладки этого кода должен быть перезапущен — старый код
  отметку не читает.
